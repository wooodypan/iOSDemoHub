# 左边一列，右边一排标签页，这套界面是怎么搭出来的

在 iPad 或者 Mac 上把这个 Demo 跑起来，你会看到左边一列分类，右边一排能关掉的标签页。点左边某个条目，右边新开一个标签，或者把当前那个预览标签替换掉。同一个条目再点一次，它不会新开，而是跳回已经存在的那个。

这套交互在 iOS 上没有现成控件可以直接拿来用。UISplitViewController 只负责把屏幕切成两半，它不知道右边该是一排能关闭的标签。UITabBarController 管的是底部几个固定入口，标签关不掉，切走的内容也未必还活着。所以这里从头手写了一遍。

代码分两层。`MultiTabController/MultiTabController/` 下面是库，只认协议，不认识任何具体内容。跟它平级的那层是 Demo，放示例列表、示例详情页和一份假数据。下面讲的是库这一层。

## 整体分层

整条路线大概是这个形状。

```text
RootBuilder（按设备分发）
├── iPhone  → PPTabBarController（底部标签栏）
│             └── 列表 → PPPhoneContentRouter → push 详情页
└── iPad/Mac → SplitContainerViewController（左右分栏）
              ├── 左栏 leftContainerView
              │    └── UINavigationController → PPTabBarController → 列表
              │         列表持有 PPContentRouting（协议）
              └── 右栏 rightContainerView
                   └── DetailHostViewController（多标签宿主）
                       ├── Tab 条（横向 UICollectionView）
                       └── 内容容器（当前标签的内容页）
```

这里面有一条贯穿全文的分工。左栏只负责发出"我想打开哪一个条目、用哪种方式打开"的意图，右栏只负责把这个意图变成具体界面。两边靠一个协议加一条闭包接上，互相不认识对方。

## 从窗口往下，第一层是设备分发

入口在 `RootBuilder`。它只做一件事，看当前设备是 iPhone 还是 iPad / Mac，然后调调用方传进来的某个闭包。

```swift
switch DeviceHelper.currentLayout {
case .iPhone:
    return iPhoneRoot()
case .iPadOrMac:
    return iPadOrMacRoot()
}
```

`DeviceHelper` 的判断也很短。Mac Catalyst 直接算 iPadOrMac，其它情况看 `UIDevice.current.userInterfaceIdiom` 是不是 pad。

这里用闭包，而不在里面直接 new 控制器，是为了让库能发布出去。iPhone 那一套和 iPad 那一套长什么样，只有集成方知道。库只做一件事，问清楚现在是什么设备，然后把选择权交回去。

## 分栏容器只做三件事

`SplitContainerViewController` 是 iPad / Mac 的根控制器。它内部只有三个视图，左容器、分割线、右容器，约束串成一条链，左容器贴最左边，分割线贴左容器右边，右容器再贴分割线右边。

左容器的宽度存成了一个属性约束，初始 320。这个约束后面要反复改。

第一件事是把两边的东西嵌进来。左边是一个 `UINavigationController`，右边是 `DetailHostViewController`，用的都是手写的 `addChild` 加四条贴边约束。之所以不用 `UISplitViewController`，是因为系统那个的分栏内容由它自己管，而这里需要左栏能整体滑出屏幕、宽度能自由拖、右边还要塞一个自制的多标签宿主。

第二件事是拖动分割线。分割线上挂了一个 `UIPanGestureRecognizer`，拖动时按位移增量改左栏的宽度。

```swift
case .changed:
    let currentX = gesture.location(in: view).x
    let delta = currentX - dragStartLocationX
    leftWidthConstraint.constant = clampedLeftWidth(dragStartLeftWidth + delta)
```

宽度有上下限，左栏最少 220，右栏最少留 320，中间用 min 和 max 钳住。

分割线本身也有点细节。看得见的那条其实只有 1 点宽，外面套了一个 12 点宽的透明抓取区，方便鼠标和手指点中。鼠标悬停上去，细线变蓝，中间冒出三个小圆点提示这里能拖，Mac 上光标还会换成左右箭头。

第三件事是折叠左栏。这里改的是 leading 约束，没动宽度。

```swift
leftLeadingConstraint.constant = isSidebarHidden
    ? -(leftWidthConstraint.constant + dividerHitWidth)
    : 0
```

往左平移"左栏宽度加抓取区宽度"那么多，左栏连同分割线正好整个滑出屏幕，右栏因为约束锚在分割线上，会自己往左铺满。之所以不动宽度，是因为左栏里是个列表，宽度一变，列表的每一行都要重新排版。整块平移出去，内容原样留在那儿等着滑回来。

## 左栏是一个自己写的标签栏

左栏塞进去的导航控制器，根控制器是 `PPTabBarController`。名字里有 TabBar，但它不是系统的 `UITabBarController`。

系统那个要求每个子控制器自带一个 `tabBarItem`，标签的内容跟着子控制器走。这个项目要的不是这个。它的每个标签由外部传进来的 `PPTabItem` 定义标题和图标。

```swift
public struct PPTabItem {
    public let title: String
    public let image: UIImage?
    public let selectedImage: UIImage?
}
```

切换的实现也很直白。选中某个下标以后，看这个子控制器是不是已经有父控制器，没有就 addChild 进来加约束，然后把上一个可见的藏起来，新的那个显示出来并提到最前面。

```swift
visibleViewController?.view.isHidden = true
nextViewController.view.isHidden = false
contentContainerView.bringSubviewToFront(nextViewController.view)
```

子控制器只 addChild 一次，之后切换都只是改 isHidden。所以你在一个列表里滚到中间，换到另一个 Tab 再换回来，位置还在。

对外还开放了选中色、未选中色、背景色、高度、程序化切换和切换回调。外面再包一层 `TabBarBuilder`，负责让两个数组的长度一致，数量对不上的时候取小的那个，不至于直接崩。

## 点一下列表，消息怎么走到右边

列表本身是 `ArticleListViewController`，它不知道自己在什么设备上，只持有一个协议。

```swift
public protocol PPContentRouting: AnyObject {
    func open(_ item: PPContentItem, mode: PPContentOpenMode)
}
```

`PPContentOpenMode` 只有三个值，preview、newTab、newWindow。单击和双击各发一个。

```swift
let mode: PPContentOpenMode = (DeviceHelper.currentLayout == .iPadOrMac) ? .preview : .newTab
router?.open(item, mode: mode)
```

单双击这件事有个小坑。两个手势挂在同一个 table view 上，单击那个必须写一句 `singleTap.require(toFail: doubleTap)`。不写的话，双击的第一次点击会先被当成单击处理，等于每次双击都先闪一下预览。

路由有两个实现。iPhone 上的 `PPPhoneContentRouter` 拿到意图直接 push 一个内容页，因为 iPhone 上本来也没有多标签这回事。iPad / Mac 上的 `PPSplitContentRouter` 把意图转交给右边。

```swift
case .preview, .newTab:
    detailHostResolver?(item)?.open(item, mode: mode)
```

`detailHostResolver` 是个闭包，由 `SplitContainerViewController` 在初始化的时候装进去，返回它自己那个详情宿主。这样一来，列表不需要认识分栏容器，分栏容器也不需要认识列表。

## 右边那个多标签宿主

`DetailHostViewController` 是整个项目里最长的一个文件，交互就发生在这里。

它的视图从上往下是三块。最上面一条横向的 `UICollectionView`，每个 cell 是一个标签，标题加一个关闭按钮。中间一条分隔线。下面是一个容器视图，放当前标签的内容。

标签的数据结构不长。

```swift
private struct DetailTabItem {
    let id: String
    var item: PPContentItem?
    let controller: PPContentDisplaying
    var isPreview: Bool
}
```

`controller` 是强引用。所有关于保活的说法，根都在这一条上。

标签宽度按标题文字的宽度算出来，再钳到 120 到 240 之间。标签多到一行放不下的时候，`UICollectionView` 自己横向滚。切换标签、打开新标签之后，代码会把当前选中的那个滚到屏幕中间。

## 保活保的是控制器

一个标签切走再切回来，里面的滚动位置和输入都还在。这件事值得单独拎出来讲，因为容易做错。

顺手的做法是把所有标签的 view 都挂在视图树上，切走的用 `isHidden` 藏起来。状态确实保住了，代价是每个 view 都还在参与自动布局。开十几个标签，布局计算就压在这十几个 view 上。

这里用的是另一种做法。子控制器的关系一直保持着，但视图树上同一时刻只挂当前选中的那一个。

```swift
for tab in tabs {
    if tab.id == selectedTabID {
        mountContentView(of: tab.controller)
    } else {
        detachContentView(of: tab.controller)
    }
}
```

挂上就是 addSubview 加四条贴边约束，拆下就是 `removeFromSuperview`。切走的时候视图拆掉，约束跟着失效，下次挂回来重建。标签再多，同时参与布局的内容视图也只有一张。

这样做有个副作用要自己补。视图是手动拆装的，UIKit 不会像容器控制器那样自动发 appearance 回调，所以挂载和拆卸的时候各要自己调一次。

```swift
controller.beginAppearanceTransition(true, animated: false)
controller.endAppearanceTransition()
```

不补这两句，内容页的 `viewWillAppear` 这类回调就永远不会来，它自己的刷新逻辑可能就不跑了。这是手写容器很容易漏的一步。

## 预览标签和正式标签

这是 VS Code 的那套规矩。单击文件算预览，标签字体是斜的，下次单击别的文件会把这个位置换掉。双击算正式打开，固定住，不会被换。

`openPreview` 先找有没有预览槽位。

```swift
if let index = tabs.firstIndex(where: { $0.isPreview }) {
    let previousID = selectedTabID
    load(item: item, into: index)
    selectedTabID = tabs[index].id
    refreshUI()
    // 只刷新受影响的 cell
} else {
    appendTab(for: item, isPreview: true)
}
```

有槽位就复用，没有就新开一个预览标签。`openNewTab` 不问这些，直接追加一个正式标签。

预览标签变成正式的，走的是另一条路。内容页自己知道用户改没改它，改了就往上报告一声，宿主收到以后把那个标签的标记改掉。

```swift
public func contentViewController(_ contentViewController: UIViewController,
                                  didChangeEditedState isEdited: Bool) {
    setPreview(!isEdited, for: contentViewController)
}
```

改完之后再去单击别的条目，因为已经找不到预览槽位，`openPreview` 会走新开那一支，不会把正在看的东西顶掉。这就是那套行为想要的效果。

另外有个开关叫 `deduplicateOpenedItems`，默认开着。开着的时候，打开一个已经打开过的内容不会新开标签，直接跳到那个标签上。比较用的是 `PPContentItem.id`，所以业务 id 得保证在同一个宿主里唯一。

## 库怎么做到不认识你的内容

这处取舍我比较想聊。

宿主得能创建内容页，可库又不能知道内容页是什么类。办法是让集成方在初始化的时候传一个工厂进来。

```swift
public typealias PPContentViewControllerProvider = () -> PPContentDisplaying
```

每新建一个标签就调一次，拿到一个全新的内容页实例。库对内容页的要求只有两条，能被内容项配置，能接受一个上报通道。

```swift
public protocol PPContentDisplaying: UIViewController {
    var contentHost: PPContentHosting? { get set }
    func configure(with item: PPContentItem)
}
```

反方向是 `PPContentHosting`。内容页通过它往上说话，比如"我编辑了"或者"我想在新标签里打开这个"。宿主实现这个协议，把这两句话翻译成具体动作。

有一条写法上的要求必须提醒，`contentHost` 得是 weak。宿主的 tabs 数组强引用着内容页，内容页要是也强引用宿主，两个对象就互相锁死了，谁也放不掉。协议注释和示例代码里都写了这一条。

## 几个真跑起来才会撞到的问题

### 标签条的更新别做全量刷新

切标签、开标签、关标签，如果每次都 `reloadData`，整条标签栏的 cell 都要重建，布局也要重算一遍。实际上每次变化只涉及一两个 cell。所以这里写了一个 `updateTabBar`，按需 reload、insert、delete。

它还有个前置动作。

```swift
view.layoutIfNeeded()
collectionView.performBatchUpdates { ... }
```

这句不能省。标签栏在没有标签的时候是收起来的，高度约束是 0。第一次插入 cell 的时候如果不先强制布局一次，`UICollectionView` 会拿着高度还是 0 的旧尺寸去插入，flow layout 这时候根本不会去问 `sizeForItemAt`，新 cell 的宽高全是 0。等后面把高度撑回 44，它也不会自己纠正回来，标签就一直是扁的。

### 删除和刷新不能塞进同一批

关掉一个标签的时候，被删掉的索引和顶上来的那个标签的新索引可能是同一个。`deleteItems` 和 `reloadItems` 都按这一批开始之前的状态去解释索引，放进同一批就撞车，抛 `NSInternalInconsistencyException`。

所以删除先做，选中态放到完成回调里按新索引再刷一次。

```swift
collectionView.performBatchUpdates({
    self.collectionView.deleteItems(at: [IndexPath(item: index, section: 0)])
}) { _ in
    if wasSelected, let newIndexPath = self.tabBarIndexPath(ofTabID: self.selectedTabID) {
        self.collectionView.reloadItems(at: [newIndexPath])
    }
}
```

### 侧栏按钮不在本站主里干活

标签条最左边有个按钮，点一下折叠或者展开左栏。按钮长在 `DetailHostViewController` 里，可折叠这个动作是 `SplitContainerViewController` 的事。所以按钮的点击只是往外发一个回调。

```swift
@objc private func sidebarButtonTapped() {
    onToggleSidebarRequest?()
}
```

父容器接到以后调自己的 `toggleLeftSidebar`，折完了再反过来通知详情宿主一声，让它把图标换成对应的那个。图标得跟左栏的实际状态对上，不然会出现图标显示可以展开、左栏其实已经开着的情况。

## 快捷键和生命周期

⌘W 用来关当前标签，在 iPad 和 Mac 上要分开处理。iPad 走 `UIKeyCommand` 就够了。Mac Catalyst 上不行，因为 ⌘W 在系统菜单里登记过，是"关闭窗口"的按键等价，AppKit 处理它的顺序比 UIKeyCommand 早。等轮到 UIKeyCommand，窗口已经在关了。

这里的办法是装一个 `NSEvent` 本地事件监听，在按键等价匹配之前把事件截住，自己把当前标签关掉，然后吞掉这个事件，不让它继续走到关窗口那一步。监听器会被详情宿主强持有，实例活着监听就生效，实例释放监听自动卸掉。

生命周期这块，库同时兼容 UIScene 和传统 AppDelegate 两种。它没有假设宿主用哪一种，判断放在运行时，用 `AppLifecycle` 来做。判据跟 Apple 技术说明 TN3187 里的两条一致，Info.plist 里有非空的场景配置，或者 AppDelegate 实现了返回场景配置的那个方法。

库内部要取窗口的地方，统一走 `AppLifecycle.activeWindow`。Scene 生命周期下它从窗口场景里找 keyWindow，传统生命周期下它读 AppDelegate 的 window 属性。所以不管宿主用哪套，库的行为都一样。

建窗口的入口是 `RootBuilder.makeWindow`，两个重载，一个带 `windowScene:` 一个不带，业务代码只需要换调用。

## 想读代码从哪儿下手

如果只想挑几条线看，我建议按这个顺序。

先看 `RootBuilder` 和 `DeviceHelper`，加起来几十行，把按设备分发这条说清楚了。

再看 `SplitContainerViewController`，把左右怎么摆、宽度怎么钳、折叠怎么做弄明白。

然后是 `DetailHostViewController`。这个文件最长，但结构就四件事，标签条的数据、内容视图的挂载拆卸、预览与正式的判断、批量更新的调用点。剩下的是注释和边界处理。

最后回头看 `PPContentDisplaying` 和 `PPContentRouters` 这两个协议文件，加起来一百多行。库能不认识内容，全靠这两个文件把边界划开。
